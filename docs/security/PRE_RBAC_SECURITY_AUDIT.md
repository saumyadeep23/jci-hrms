## Executive Summary

JCI HRMS is a substantially more mature Spring Boot 3.3.2 / Java 21 / React 19 application than its own `CLAUDE.md` currently describes (that file's "only an Employee entity exists" framing is stale — Payroll, CPF, JCIECCS, Attendance, Leave, APAR, and document-upload domains are all implemented with 94 Flyway migrations and 96 REST controllers). The codebase shows real security engineering maturity in several places — a consistently applied object-level "SELF-scope" authorization pattern (`*Security.isSelf(...)` beans), genuinely least-privilege Terraform IAM, a well-designed file-upload pipeline, SSRF-safe outbound integrations, and — most notably — JCIECCS Phase 5's idempotency-key + pessimistic-locking + fixed-lock-ordering concurrency architecture, which is the strongest financial-integrity engineering in the repository.

Against that, this audit found **4 CRITICAL and 2 HIGH-severity findings that should be treated as blocking or near-blocking** before any RBAC/onboarding work proceeds on top of them:

1. **SEC-001** — The JWT authentication layer has no production fail-closed guard: if deployed as-is (Terraform sets no `JWT_ISSUER_URI`/`JWT_LOCAL_DEV_SECRET`/`SPRING_PROFILES_ACTIVE` today), the app silently authenticates with a hardcoded, source-visible HMAC secret, allowing anyone to forge a JWT with arbitrary role **and** employee-identity claims — a full authentication and authorization bypass.
2. **SEC-002** — `POST /api/attendance/punch` has no role check at all (`isAuthenticated()` only) and no ownership check, letting any authenticated user fabricate another employee's time and GPS-location attendance record.
3. **SEC-003 / SEC-004** — Neither the CPF loan lifecycle nor JCIECCS recovery/reversal enforce maker≠checker: a single role-holder can originate and approve/disburse/reverse the same financial transaction.

Three further object-level authorization gaps (SEC-005/006/007) follow the same root-cause pattern as SEC-002 on lower-traffic self-service creation endpoints (attendance regularization, leave encashment, leave application). The remaining findings are MEDIUM/LOW hardening items (CI/CD supply-chain pinning, dependency scanning, security headers, formula-injection in XLSX export, TOCTOU error handling) that do not block RBAC design but should be scheduled.

**No application code, configuration, database schema, or data was modified during this audit.** All deliverables are documentation under `docs/security/`.

## Authentication

`backend/src/main/java/in/gov/jci/hrms/security/SecurityConfig.java` establishes a stateless JWT resource server. `JwtDecoder` (lines 120-127) uses `JwtDecoders.fromIssuerLocation(issuerUri)` when `spring.security.oauth2.resourceserver.jwt.issuer-uri` is non-blank; otherwise it falls back to `NimbusJwtDecoder.withSecretKey(...)` using `security.jwt.local-dev-secret` (HS256). `application.yml` sets `issuer-uri: ${JWT_ISSUER_URI:}` (blank default) and `local-dev-secret: ${JWT_LOCAL_DEV_SECRET:local-dev-only-secret-key-never-use-in-production-32bytes}` (a literal default value, committed to source control). `JwtRoleConverter.java` maps `realm_access.roles`/`resource_access.*.roles` JWT claims directly to `ROLE_*` `GrantedAuthority`s with no allow-list or validation beyond signature verification. `SecurityUtils.currentEmployeeId()` (`security/SecurityUtils.java`) reads an `employee_id` claim directly from the JWT as the sole link between an authenticated principal and an Employee row — there is no separate user table.

**Production path**: intended to be `JwtDecoders.fromIssuerLocation(issuerUri)` against a real OIDC IdP — **not yet provisioned for any environment** (no IdP exists per `CLAUDE.md` and confirmed by the absence of any issuer configuration anywhere in Terraform).

**Development path**: HS256 with the local-dev secret — used correctly today for local dev, CI, and the app's own test suite (which mints its own tokens via `spring-security-test`).

**Fallback path — this is the finding**: the *same* fallback activates in any environment, including a hypothetical production deploy, purely because `issuer-uri` is blank. There is no `SPRING_PROFILES_ACTIVE`-based guard, no explicit production-vs-development branch, and no startup assertion anywhere in the codebase. `infra/main.tf`'s ECS task definition (lines 360-383) sets only `SPRING_DATASOURCE_URL`/`USERNAME`/`PASSWORD` as environment/secrets — it configures **neither** `JWT_ISSUER_URI` **nor** `JWT_LOCAL_DEV_SECRET` **nor** any profile marker. A deploy of the current Terraform + current jar would silently run on the hardcoded default HS256 secret.

### SEC-001 — HS256 fallback has no production fail-closed guard (CRITICAL)

- **Status:** NON_COMPLIANT. **Severity:** CRITICAL. **Remediation:** BLOCK_BEFORE_RBAC / BLOCK_BEFORE_PRODUCTION.
- **Affected:** `backend/src/main/java/in/gov/jci/hrms/security/SecurityConfig.java:120-127`, `backend/src/main/resources/application.yml`, `infra/main.tf:360-383`.
- **Evidence:** as described above — no branch on environment/profile anywhere in the fallback path; default secret is a literal string in version control; Terraform never overrides either the issuer or the secret.
- **Attack scenario:** An attacker who can read the (GitHub-hosted) source — or simply knows this is a common default-secret pattern and brute-forces/reads the repo — computes an HMAC-SHA256 signature using the known default secret, mints a JWT with `realm_access.roles: ["SUPER_ADMIN"]` and any `employee_id` claim they choose (e.g., the future bootstrap ID 8), and presents it as a bearer token to any endpoint. Because `JwtRoleConverter` performs no additional validation, the forged token is accepted as a fully authenticated `SUPER_ADMIN` request.
- **Impact:** Complete confidentiality, integrity, and availability compromise — full authentication and authorization bypass, including every financial and PII endpoint in the system. This also invalidates every object-level `isSelf` check documented in `CURRENT_AUTHORIZATION_MODEL.md`, since those checks trust the same forgeable `employee_id` claim.
- **Recommendation:** Add a startup-time fail-closed guard: refuse to start (or refuse to build the `jwtDecoder` bean) when a "production-shaped" profile is active and `issuer-uri` is blank, or when `local-dev-secret` still equals its literal default value. Provision a real OIDC IdP before any non-dev deployment. Do not implement this during the current audit task (per its explicit read-only scope) — carry it into the RBAC/production-hardening track as the first item.
- **Verification:** An integration test asserting the application context fails to start (or the relevant bean throws) when `issuer-uri` is blank and a production-marker profile/property is set.
- **OWASP:** A07:2021 (Identification and Authentication Failures); API Security Top 10 API2:2023 (Broken Authentication). **CWE:** CWE-798 (Use of Hard-coded Credentials), CWE-321 (Use of Hard-coded Cryptographic Key).

## Authorization

Full inventory and matrix: `docs/security/CURRENT_AUTHORIZATION_MODEL.md`. Summary: 100% method-security (`@PreAuthorize`/`@Secured`), zero URL-pattern role gating beyond the 4 `permitAll` paths. Exactly 7 role strings exist today (`SUPER_ADMIN`, `HR_ADMIN`, `FINANCE_ADMIN`, `CPF_ADMIN`, `COOP_ADMIN`, `BILL_SUPERVISOR`, `EMPLOYEE`); `SUPER_ADMIN` is a de facto god-role present in ~85 of ~260 `@PreAuthorize` expressions, with no existing separation between technical administration and financial approval authority (directly relevant to the future `SYSTEM_ADMIN` boundary requirement, spec §15). A mature, mostly-correctly-applied object-level "SELF-scope" pattern already exists (`EmployeeSecurity`, `LoanSecurity`, `CpfApplicationSecurity`, `LeaveApplicationSecurity`, `AparSecurity`, `@jciEccsSec`, plus JWT-derived-identity self-service reads for salary slips/CPF passbook/attendance history) — this is the correct template to generalize during RBAC, not a mechanism to replace. No organizational data scope (`SELF`/`OFFICE`/`REGION`/`HO`/`ALL_JCI`) exists anywhere yet; today every role check is effectively `ALL_JCI`-wide.

## IDOR/BOLA

**Result: four confirmed findings, all sharing one root cause.** Every *read/update/approve* self-service endpoint correctly enforces object-level ownership (salary slips, CPF passbook, attendance history, employee sub-resources, loans, APAR). The gap is specifically on **creation** endpoints that accept a client-supplied `employeeId` in the request body without checking it against the caller:

- **SEC-002 (CRITICAL)** — `POST /api/attendance/punch` (`MobilePunchController.java:33-59`): `@PreAuthorize("isAuthenticated()")` only, **no role restriction whatsoever**, and `MobilePunchService.create()` loads the target employee directly from the client-supplied `employeeId` with no ownership or role check. Any authenticated user — any role — can fabricate a time-stamped, geolocated attendance punch for any other employee. This is a write, not just a read, directly falsifying data that feeds payroll and leave-deduction logic, and directly undermines the punch-level geofence evidence the future Attendance Engine is meant to preserve. Independently corroborated by two separate research passes in this audit.
- **SEC-005 (HIGH)** — `POST /api/v1/attendance/regularization` (`AttendanceRegularizationController.java:40-44`): role-gated (`EMPLOYEE`/`HR_ADMIN`/`SUPER_ADMIN`) but not ownership-checked; a falsified regularization request is routed to the *real* target employee's approver.
- **SEC-006 (HIGH)** — `POST /api/v1/self-service/leave/encashment` (`LeaveEncashmentController.java:37-41`): same shape, with a direct financial-payout consequence — an attacker can consume another employee's leave balance via a real encashment claim.
- **SEC-007 (MEDIUM)** — `POST /api/leave-applications` (`LeaveApplicationController.java:33-36`): same shape but contained impact, since the created record starts as `DRAFT` and the subsequent `submit()` step remains correctly `isSelf`-gated (the attacker cannot advance the workflow themselves).

**Fix pattern (identical for all four):** derive `employeeId` server-side from `SecurityUtils.currentEmployeeId(authentication)` — the pattern already correctly used by `EssPayrollController`, `AttendanceHistoryController`, and `CpfSelfServicePassbookController` — unless the caller holds an explicit role authorized to act on another employee's behalf, in which case that role (not mere authentication) should gate the override.

No BOLA finding exists on identifier predictability alone — all reviewed IDs are sequential JPA-generated longs, but this only matters combined with a missing ownership check, which is exactly the situation above (and in three of the four cases, the attacker doesn't even need to guess an ID — they name the victim directly in the request body).

## Maker-Checker

**Current readiness: not implemented in any financial domain.** CPF (`CpfLoanController`/`CpfLoanApplicationService`) and JCIECCS (`JciEccsRecoveryService`) both gate the entire lifecycle — create/apply through sanction/disburse/reverse — with one identical role set, and neither service compares the "maker" actor against the "checker" actor anywhere (SEC-003, SEC-004, both CRITICAL). This is architecturally different from the BOLA findings above: it cannot be patched with a simple ownership check, because "maker" and "checker" aren't distinct roles yet in the current 7-role model — it requires the RBAC phase's `FIN_MAKER_CPF`/`FIN_ADMIN_CPF`, `JCIECCS_MAKER`/`JCIECCS_ADMIN` split, enforced with `maker_user_id != checker_user_id` at the service layer (not just UI/role separation, which the audit spec correctly identifies as insufficient). Payroll's batch-edit/finalize/reversal lifecycle was not independently re-verified for the same pattern in this pass (flagged as a likely-present follow-up, given it uses the identical controller-level `@PreAuthorize` convention as CPF/JCIECCS) — recommend a targeted spot-check before RBAC implementation begins.

**Positive finding:** JCIECCS's actor-persistence (`performedByEmployeeId` stored on every recovery/reversal row) is a real improvement over CPF, which persists no actor identity at all (SEC-008, HIGH) — there is no `@EnableJpaAuditing`/`AuditorAware`/`@CreatedBy` anywhere in the entire application, so CPF loan sanctions/disbursements cannot be forensically attributed from stored data today.

## SYSTEM_ADMIN Boundary

No existing separation between technical administration and financial approval authority. `SUPER_ADMIN` today implicitly carries both (SEC-010, MEDIUM) — see Authorization section above. The future `SYSTEM_ADMIN` role must be designed as a genuinely non-financial role from the start; there is no partial migration to build on, which is actually the simpler starting position (a clean design, not an unwind).

## Onboarding Security

No onboarding/invitation/activation implementation exists in this codebase today beyond a draft-capture DTO/repository (`EmployeeOnboardingDraftRepository`, `OnboardingDraftUpsertRequest` — deliberately unvalidated as a draft-save envelope, full validation only at a future `finalize()` step per its own javadoc). No invitation-token model, no activation controller, no bootstrap-employee-ID-8 logic exists yet. This means: (a) there is currently no live onboarding attack surface to assess, and (b) the future design (spec §17-19) must be built with the findings in this audit in mind — see `docs/security/ONBOARDING_SECURITY_REQUIREMENTS.md` for the full translated requirement set. The bootstrap-bypass check (spec §18) found no `employeeId == 8` or equivalent logic anywhere — clean today, but must be re-tested the moment bootstrap logic is added.

## API Security

Input validation is broad and consistent: 153 of 166 sampled request DTOs carry Bean Validation constraints; the 6 without are all legitimate by design (boolean-only payloads, business-rule-deferred drafts, or misnamed response DTOs). Mass assignment: **zero** controllers bind a JPA entity directly as a request body (138 distinct request-body DTO types cross-referenced against 289 entity classes — no overlap) — all mutation flows go through purpose-built DTOs. SQL injection: all 9 `nativeQuery` usages are fixed-literal SQL with bound parameters; all reviewed `JdbcTemplate` usage is either fully parameterized or built from hardcoded allow-lists, with one LOW hardening item (SEC-013 — `AlmsReportService` concatenates a Java-built numeric ID list into `IN (...)` text; not currently exploitable since the values are DB-sourced, but architecturally brittle). XSS: zero `dangerouslySetInnerHTML`/`.innerHTML`/`eval(` in the frontend; PDF/XLSX generation writes values directly (not through a template/expression engine), except one MEDIUM finding: **SEC-012**, CSV/formula-injection in `XlsxExportService.java:97-103` (`setCellValue()` with no `=+-@` prefix-escaping — CWE-1236). SSRF: **compliant** — the two outbound integrations (India Post pincode, Razorpay IFSC) use fixed base URLs, strict input regex validation before use, and URI-template parameter binding, so no user input can influence scheme/host/port. Deserialization, command execution, open redirect, and SSR/template injection: **no findings** — none of the relevant sinks (`ObjectInputStream`, unsafe Jackson polymorphic typing, `Runtime.exec`/`ProcessBuilder`, `sendRedirect`, template-engine dependencies) exist anywhere in the codebase.

## Input Validation

See API Security above. No systemic gap found; the 6 unvalidated DTOs are all justified by design and documented in the relevant service javadocs.

## Session/Token Security

Stateless (`SessionCreationPolicy.STATELESS`), no server-side session or cookie usage anywhere — session-fixation and cookie-flag controls are `NOT_APPLICABLE` to this architecture. JWT stored client-side in `localStorage` (`AuthContext.tsx`, `api/client.ts`) rather than an httpOnly cookie — a standard SPA/bearer-token tradeoff, flagged as SEC-016 (LOW/INFORMATIONAL, HARDEN_BEFORE_FORMAL_VAPT: short token TTL, a defined CSP, and continued absence of any raw-HTML rendering are the relevant mitigations). CSRF is correctly disabled (`SecurityConfig.java:52`) — appropriate given the app is a genuinely stateless bearer-token API with no cookie-based auth; this is not a vulnerability given the actual architecture (per the audit's own instruction not to flag `csrf.disable()` reflexively).

## Financial Security

**CPF:** No maker-checker (SEC-003, CRITICAL); no actor-identity persistence anywhere in the loan lifecycle (SEC-008, HIGH); DTOs carry solid bounds validation (`@Positive`, `@Min`, `@DecimalMin` on amount/rate/installment fields); no mass-assignment path. **Payroll:** the previously-documented TOCTOU in `PayrollBatchService.create()` is confirmed and refined — the unique-constraint backstop (`uq_payroll_batch_month_year`) fully prevents actual duplication, but a genuinely concurrent duplicate request surfaces as an unhandled 500 rather than the same clean 409 the sequential path returns, because `GlobalExceptionHandler` has no `DataIntegrityViolationException` handler (SEC-009, MEDIUM — integrity is not at risk, this is a response-consistency/observability gap). Payroll's edit/finalize/reversal maker-checker posture was not independently re-verified in this pass and should be spot-checked before RBAC implementation (likely to share the CPF/JCIECCS pattern, given the identical `@PreAuthorize` convention). **JCIECCS:** genuinely strong concurrency/idempotency engineering (idempotency keys on payroll/cash/reversal recovery paths, pessimistic row locks with documented fixed lock ordering to prevent deadlocks, actor-identity persistence on every transaction) — but the same maker-checker gap as CPF (SEC-004, CRITICAL): a single role-holder can create and immediately reverse the same recovery. `JciEccsMemberController`'s `@jciEccsSec.isSelf(...)` pattern is a genuine SELF-scope precedent worth generalizing.

## PII/Data Protection

`Employee` entity carries PAN, Aadhaar reference number, personal/official email, phone numbers, PRAN/UAN, and CPF account number; `EmployeeBankAccount` holds bank details separately. List/search endpoints return purpose-built DTOs (not raw entities) — structurally compliant with the minimization principle — but field-by-field masking on list views specifically (does `EmployeeResponse` on a list call omit PAN/Aadhaar the way a single-record view might legitimately include them?) was not exhaustively diffed in this pass (SEC-027, `REQUIRES_BUSINESS_CONFIRMATION`, to be resolved during RBAC's field-level-security design, spec §71). No sensitive-field logging was found anywhere (zero matches for JWT/password/secret/Aadhaar/bank/salary/PII in any `log.*` call across the backend). No unbounded "export everything" endpoint was found for employees, salaries, CPF balances, attendance, or bank details.

## Attendance/Geolocation Security

Raw-coordinate retrieval (`MobilePunchController.getById()`/`list()`) is correctly restricted to `HR_ADMIN`/`SUPER_ADMIN`, and the employee's own history view (`AttendanceHistoryController.myHistory()`) is correctly SELF-scoped via the JWT claim, not a request parameter — both genuinely compliant controls. The severe gap is on the **write** side: `POST /api/attendance/punch` has no ownership or role check at all (SEC-002, covered fully under IDOR/BOLA above) — geolocation and time data can be fabricated for any employee by any authenticated user, which is the most severe individual finding outside of SEC-001.

## File/Report Security

**Upload** (`DocumentUploadController`/`DocumentUploadService`/`UploadCategoryPolicy`/`LocalStorageServiceImpl`): genuinely well-designed — category-scoped MIME **and** extension allow-lists (only `image/jpeg`, `image/png`, `application/pdf` permitted across all 16 categories, meaning no SVG/HTML/script-capable type is ever accepted), magic-byte content validation that defeats extension/MIME spoofing, per-category size caps layered on top of Spring's global multipart limits, sanitized filenames (`[A-Za-z0-9._-]` only, UUID-prefixed storage keys with no user-controlled path segments), and a second independent path-traversal guard in `LocalStorageServiceImpl.resolve()` that normalizes and re-validates the resolved path even if upstream sanitization were somehow bypassed. **Download**: no endpoint exists yet anywhere in the backend (`DocumentStorageService` exposes only `store()`) — flagged forward (SEC-014, INFORMATIONAL/`INCORPORATE_IN_RBAC`) so that ownership tracking (`entityRefId` is currently accepted but not persisted) is designed in before a retrieval endpoint is built, rather than retrofitted. **Reports**: PDF generation via PDFBox is direct content-stream text drawing (no template/expression-injection surface); XLSX export via Apache POI has the one MEDIUM formula-injection hardening item (SEC-012) noted above; `AdHocReportService`'s dynamic SQL reporting uses a hardcoded column allow-list with bound parameter values — reviewed and safe.

## Logging/Audit

No sensitive-data logging found (JWT/Authorization headers, passwords, secrets, Aadhaar, bank details, salary, PAN, UAN, CPF account numbers, geolocation — all zero matches across `log.*` calls). Financial audit-trail maturity is inconsistent across domains: JCIECCS persists actor identity per transaction (good); CPF resolves the actor correctly at the controller layer but never persists it (SEC-008); Payroll has a `payroll_edit_logs` table (per the prior baseline-repair doc) whose actor-identity coverage was not independently re-verified in this pass. No endpoint was found that allows a normal authenticated user to modify or delete audit-trail rows (`JciEccsAuditTrailController` exposes read-only mappings in the sampled review). Error handling is sanitized for the ~13 specific business exceptions `GlobalExceptionHandler` covers, but there is no catch-all handler (SEC-017, INFORMATIONAL) — not a leak given Spring Boot's safe defaults, but a gap that directly produces the SEC-009 TOCTOU symptom.

## Database Security

`ddl-auto: validate` (Flyway-only schema management, no Hibernate auto-DDL in any environment) — `application.yml`. DB credentials sourced from AWS Secrets Manager via the ECS task's `secrets` block in every environment (not a plaintext env var) — confirmed in Terraform, not just trusted from `CLAUDE.md`. Production database-user privilege scoping (whether the app's DB user has only the privileges it needs, vs. broader schema-owner rights) cannot be verified from this repository — `REQUIRES_INFRA_VERIFICATION`. `uq_payroll_batch_month_year` and similar unique constraints function as genuine defense-in-depth backstops beneath service-layer validation (see SEC-009 discussion of what happens when that backstop is the only thing that fires).

## RBAC Implications

Translated into concrete requirements: `docs/security/RBAC_SECURITY_REQUIREMENTS.md`. Headline items: SEC-001 must be closed before RBAC is meaningful (forgeable identity undermines any role/scope model built on top of it); SEC-003/004/008/010 are precisely what the RBAC maker-checker and SYSTEM_ADMIN-boundary requirements exist to fix, and should be designed together rather than sequentially; the existing `isSelf`/JWT-derived-identity pattern is the correct foundation to generalize for SELF/OFFICE/REGION/HO/ALL_JCI scoping, not a mechanism to discard.

## Pre-Production Requirements

SEC-001 (auth fail-closed) and SEC-002 (attendance-punch authorization) should be remediated before or in immediate parallel with the start of RBAC work — both are narrowly-scoped, fast-to-fix bugs, not architecture changes, and leaving either open during a multi-week RBAC build leaves a live, trivially exploitable hole in a system already this far along. SEC-005/006/007/012/023 should be scheduled as near-term fixes. SEC-018/019/020/021/022 are hardening items appropriate for the formal-VAPT-readiness pass. SEC-026 (HTTPS) and SEC-024 (Terraform state backend) are infrastructure work items to schedule before any staging/prod rollout, independent of the RBAC timeline.

## Formal VAPT Readiness

**This internal source/configuration security assessment does not constitute an external VAPT certificate, a CERT-In audit, an STQC audit, or Safe-to-Host certification.** It is a pre-RBAC internal readiness review only.
