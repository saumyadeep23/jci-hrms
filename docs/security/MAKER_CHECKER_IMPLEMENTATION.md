# Maker-Checker Implementation

## Generic rule (RBAC_SECURITY_REQUIREMENTS.md §7 / instruction 45)

Enforced at the **service layer**, not `@PreAuthorize`/UI: `maker_user_id != checker_user_id`, compared as plain `Long` equality against a persisted actor column, throwing `org.springframework.security.access.AccessDeniedException` (→ 403, standard Spring Security handling, no new exception-mapping code needed) on violation. A user holding both maker and checker roles/permissions is still blocked, because the check compares **actual persisted actors on the specific transaction**, not role membership.

## CPF (SEC-003)

**Lifecycle covered**: apply → sanction → disburse → settle-cash. `settle-cash` (`CpfLoanSettlementService.processCashSettlement`) was flagged as a follow-up in the original phase and closed in the 2026-09-16 SEC-010 pass: it now rejects when `receivedByOfficerId` equals the loan's `applicantEmployeeId`, checked (and rejected, before any balance/ledger mutation) using the exact same pattern as `requireDifferentFromApplicant` — settlement is a financially authoritative transition (reduces outstanding balance, credits the member's EE ledger, can close the loan) exactly like sanction/disburse, so it belongs to the same maker!=checker boundary. Verified by `CpfLoanTwoPhaseAndSettlementTest.settleCash_bySameOfficerWhoApplied_throwsAccessDeniedAndAppliesNoMutation` / `settleCash_byDifferentOfficerThanApplicant_allowed`.

- V96 migration adds `applicant_employee_id`, `sanctioned_by_employee_id`, `disbursed_by_employee_id`, `rejected_by_employee_id` to `cpf_loan_applications` (plain `BIGINT`, no FK — matching JCIECCS's own `created_by` convention).
- `CpfLoanApplicationService.applyLoan()` persists `applicantEmployeeId`.
- `sanctionLoan()`/`disburseLoan()` call `requireDifferentFromApplicant(loan, actingOfficerId, action)` **before** any state mutation — rejection produces zero side effects (verified: `sanctionLoan_bySameOfficerWhoApplied_throwsAccessDenied` asserts the application status remains `APPLIED` after the rejected attempt).
- `rejectLoan()` persists `rejectedByEmployeeId` for attribution but does **not** enforce maker≠checker (rejection is a low-risk, no-funds-movement action — a reasonable, explicitly-noted judgment call, not an oversight).
- Historical rows (pre-V96) have `applicant_employee_id = NULL` → `requireDifferentFromApplicant` never blocks them (nothing to compare against) — no retroactive lockout.

Role mapping to `FIN_MAKER_CPF`/`FIN_ADMIN_CPF` (instruction 46): defined in the V94 permission seed (`CPF_PREPARE` vs `CPF_SANCTION`/`CPF_DISBURSE`) but **not yet wired into `CpfLoanController`'s `@PreAuthorize`** — the controller still uses its legacy `hasAnyRole('FINANCE_ADMIN','CPF_ADMIN','SUPER_ADMIN')` gate. The service-layer maker≠checker check is independent of and does not require that migration to be effective (see `RBAC_MIGRATION_REPORT.md`).

## JCIECCS (SEC-004)

`JciEccsRecoveryService.reverseRecovery()`: after the existing status/idempotency checks (unchanged), a new check compares `performedByEmployeeId` against the already-persisted `original.getCreatedBy()` — same actor → `AccessDeniedException`, before the pessimistic lock chain (`loanRepository.findByIdForUpdate`/`memberRepository.findByIdForUpdate`) or any ledger/schedule mutation runs.

**Phase 5 architecture explicitly preserved, not touched**: pessimistic locking (`findByIdForUpdate`), fixed LOAN-then-MEMBER lock order, the `REVERSAL:{recoveryId}` idempotency key, recovery/allocation/ledger separation. The new check is a single in-memory `Long` comparison inserted after the row is already locked — no new I/O, no change to lock acquisition order.

Recovery *creation* (`createAndPostPayrollRecovery`, cash repayment) has no separate maker/checker split — it *is* the maker step by definition; the checker step is specifically reversal (and reconciliation/settlement, not touched this phase — see below).

## Payroll / Disbursement — verification performed, NOT implemented this phase

Per instruction 50, the actual lifecycle was inspected (not assumed) before any mapping decision:

- `PayrollBatchService` (create/compute/edit/finalize/reversal) and `PayrollBatchEditService` were **not** re-opened this phase beyond what the original Pre-RBAC audit already established (the TOCTOU finding, SEC-009 — separate, unrelated issue).
- **Finding**: no maker≠checker enforcement exists in the current Payroll lifecycle, matching the original audit's own flag ("Payroll's edit/finalize/reversal review was out of my time budget... likely present, since it's the same controller-level `@PreAuthorize` convention"). This phase did not implement a fix, for two reasons: (1) instruction 52's explicit prerequisite — "Determine exact transition ownership from existing CPF lifecycle... Do not invent new financial stages unnecessarily" — applying the same pattern to Payroll requires confirming which specific transitions (compute? edit? finalize? reverse?) are the intended maker/checker boundary, which is a business-confirmation question this phase did not resolve; (2) quota/scope discipline for this already-large phase.
- **REQUIRES_BUSINESS_CONFIRMATION**: which Payroll transition(s) constitute the maker step vs. the `HR_ADMIN_BILL` checker step, and whether `FIN_MAKER_DISB`/`FIN_ADMIN_DISB` apply to a distinct disbursement step or to Payroll finalization itself — the JCIECCS-payroll-integration lock (instruction 54, deductions sent to Payroll must stay non-editable from the Payroll side) was also not touched, and remains intact by construction (nothing in this phase modifies `PayrollBatchService`/`PayrollBatchEditService` at all).

## Test coverage

See `RBAC_SECURITY_TEST_REPORT.md` for the full list. Summary: CPF (4 new maker-checker tests in `CpfLoanApplicationServiceTest` + 2 new settle-cash tests in `CpfLoanTwoPhaseAndSettlementTest`, real-DB integration), JCIECCS (regression across `JciEccsRecoveryServiceTest`/`JciEccsFinancialInvariantSuiteTest`/`JciEccsReconciliationServiceTest`/`JciEccsConcurrencyHardeningTest` — actor ids adjusted in 4 existing tests that previously used the same actor for create+reverse, now correctly using distinct actors to match the new invariant, real-DB integration).

**2026-09-16 closure — `JciEccsConcurrencyHardeningTest.scenarioD2_reversalRacesANewRepayment_neverLosesAnUpdate` resolved, not a production defect.** Root cause (confirmed via live diagnostic tracing before any fix, then reverted): the test's cash-repayment idempotency key was a hardcoded literal (`"IDEMP-RACE-D2"`, not derived from the class's own per-invocation `seq` counter used for every other fixture). A 2026-09-15 test run left a permanent orphaned `jcieccs_recovery` row under that exact key (id=678, member/loan/allocation/loan_repayment fixtures all still present — that run's `tearDown()` never fully completed). Every subsequent run of the scenario hit `createAndPostCashRecovery`'s idempotency short-circuit against that stale row and silently applied zero balance effect, deterministically reproducing `expected 115000.00 but was 120000.00` on 100% of runs. **The JCIECCS Phase 5 concurrency/locking engine itself was not implicated** — instrumented tracing confirmed correct lock acquisition/serialization on both sides of the race; the only defect was test-side. Fix: (1) the one identified residue row (id=678) and its exact allocation/loan_repayment dependents were deleted (user-approved; no `deleted_at` soft-delete convention exists on this table, so this followed the same hard-delete pattern the test's own `tearDown()` already uses, scoped to only those 3 rows), (2) every `RACE-*` literal (idempotency keys, receipt/challan/transaction references) across all 6 scenarios in the class now includes the per-invocation `seq` suffix so this class of collision cannot recur even if a future run's cleanup fails, and (3) `tearDown()`'s three recovery/allocation/loan_repayment delete loops now catch per-row instead of per-batch, so one row's delete failure can no longer abort cleanup of its siblings (the mechanism that let 2026-09-15's partial failure become a *permanent* orphan). Verified: the single test, the full 6-test class, and the full 106-test JCIECCS regression suite all pass 0 failures/0 errors after the fix.
